# SAMERIDER（Same-sized Raster Image Divider, Editor and Recomposer） 実装計画

## 0. 目的

ゲーム制作者向けの、直感的なスプライトシート編集・管理ツールを作成する。

一般的な画像編集ソフトではなく、

**「Excelのセルを操作する感覚でスプライトシートを組み立てる」**

ことを基本コンセプトとする。

主な用途は以下。

- 個別PNGからスプライトシートを作成する
- 大きな連結画像を自動分割して配置する
- 既存の配置を後から入れ替える
- 各フレームの位置を1px単位で微調整する
- 前後フレームを重ねてアニメーションの繋がりを確認する
- 編集状態をJSONプロジェクトとして保存・復元する
- 最終的なスプライトシートPNGを書き出す

技術に詳しくないユーザーでも扱えることを最優先する。

---

# 1. 技術構成

## 1.1 基本構成

Windows / macOS向けクロスプラットフォーム・デスクトップアプリとして実装する。

採用技術：

- C#
- .NET 8
- Avalonia UI
- System.Text.Json
- AvaloniaのBitmap / WriteableBitmap等による画像表示
- 必要に応じてクロスプラットフォーム対応の画像処理ライブラリを使用する

MVVMは必要以上に複雑化しない。

WindowsとmacOSの両方で同一のプロジェクトデータを読み書きできることを前提とする。

Windows固有API、WPF、WinFormsには依存しない。

### ファイル操作

ファイル選択・保存先選択にはAvaloniaの `StorageProvider` APIを使用する。

- `OpenFilePicker`
- `SaveFilePicker`

等、現在のAvaloniaで推奨されているAPIを使用し、旧式・非推奨のFileDialog APIを前提にしないこと。

### Drag & Drop

外部PNGファイルのドラッグ＆ドロップにはAvaloniaのDrag & Drop APIを使用する。

OS固有のD&D APIへ直接依存しない。

### キーボード操作

以下のキーボード操作をWindows / macOSの両方で利用可能にする。

- 保存
- Undo / Redo
- Arrow Keyによるセル位置調整
- その他ショートカット

保存等の一般的なショートカットについてはOS差を考慮する。

例：

- Windows: Ctrl+S
- macOS: Cmd+S

可能な限りAvaloniaのKeyBinding / HotKey等、クロスプラットフォームな仕組みを使用する。

### ウィンドウ終了

ウィンドウのClosing処理を捕捉し、Dirty状態の場合は保存確認を行う。

Windowsの×ボタン、Alt+F4、macOSのウィンドウ終了操作等について、可能な限り同一の保存確認フローを通す。

### 画像処理

画像処理ロジックはAvalonia UIから分離する。

以下をUIイベントへ直接実装しない。

- Import
- Split
- Crop
- Padding
- Offset
- Composite
- Export

画像処理層はWindows / macOS共通コードとする。

### 配布

同一ソースコードから、

- Windows x64
- macOS Apple Silicon（arm64）
- 必要であればmacOS Intel（x64）

向けに個別ビルドを生成できる構成にする。

Windows用実行ファイルとmacOS用アプリケーションは別々の配布物として生成する。

macOS向け配布については、実装完了後にコード署名・Gatekeeper・Notarization等の配布上の要件を別途検討する。

# 2. プロジェクト構造

1つの編集プロジェクトは以下のような構造とする。

```text
MyAnimation/
├─ MyAnimation.json
└─ assets/
   ├─ idle.png
   ├─ walk.png
   ├─ attack.png
   └─ ...
```

外部から画像を読み込んだ場合、元ファイルを直接参照しない。

必ず `assets` 内へコピーし、以後はコピーされたファイルを参照する。

JSON内の画像パスは絶対パスではなく、JSONファイルからの相対パスとする。

例：

```json
{
  "title": "MyAnimation",
  "cellWidth": 100,
  "cellHeight": 100,
  "columns": 8,
  "rows": 4,
  "cells": [
    {
      "x": 0,
      "y": 0,
      "source": "assets/walk.png",
      "sourceCellX": 0,
      "sourceCellY": 0,
      "offsetX": 0,
      "offsetY": 0,
      "displayName": "walk_01"
    }
  ]
}
```

JSONスキーマは将来変更に備え、

```json
"formatVersion": 1
```

を持たせること。

# 5. グリッド

## 5.1 セル設定

以下を設定可能にする。

- Cell Width
- Cell Height
- Columns
- Rows

例：

```text
Cell: 100 × 100 px
Grid: 8 × 4
```

各セルには画像を1つ表示できる。

空セルも許可する。

# 6. セルへの画像読み込み

## 6.1 セルクリック

空セルまたは既存セルをクリックするとファイル選択ダイアログを開く。

PNG画像を選択して配置する。

専用の「画像を読み込む」ボタンは作らない。

---

## 6.2 ドラッグ＆ドロップ

PNGを任意のセルへD&Dできる。

D&D先セルを配置開始位置とする。

---

# 7. 画像サイズ判定

セルサイズを

```text
CW × CH
```

とする。

読み込んだ画像サイズを

```text
IW × IH
```

とした場合、

```text
IW % CW == 0
IH % CH == 0
```

の両方を満たすことを必須とする。

満たさない場合は読み込みを拒否する。

例：

```text
セルサイズ: 100 × 100
画像サイズ: 250 × 100
```

の場合、

```text
この画像は現在のセルサイズの整数倍ではありません。

画像: 250 × 100 px
セル: 100 × 100 px
```

とエラー表示する。

画像の自動縮小・拡大は行わない。

---

# 8. 大画像の自動分割

画像サイズがセルサイズより大きく、整数倍の場合は自動的に複数セルへ展開する。

例：

```text
Cell = 100 × 100
Image = 400 × 200
```

なら、

```text
4 × 2 cells
```

として扱う。

D&Dまたはクリックしたセルを左上として、

```text
01 02 03 04
05 06 07 08
```

の順で配置する。

元画像そのものを8ファイルへ物理分割する必要はない。

各セルは、

- source image
- sourceCellX
- sourceCellY

を保持し、同一画像の異なる領域を参照する。

---

# 9. グリッド外へのはみ出し

複数セル画像を配置した結果、現在のColumns / Rowsからはみ出す場合は勝手に切り捨てない。

確認ダイアログを表示する。

例：

```text
画像を配置するにはグリッドサイズを
8×4 → 10×5
へ拡張する必要があります。

グリッドを拡張しますか？

[拡張して配置] [キャンセル]
```

縮小は自動で行わない。

---

# 10. ファイルコピー

画像を読み込んだ時点で、画像をプロジェクトの `assets` フォルダへコピーする。

元ファイルは以後参照しない。

これにより、

- 元画像の移動
- 元画像の削除
- 外付けドライブの取り外し

などによる参照切れを防止する。

同名ファイルが存在する場合は不用意に上書きしない。

例：

```text
walk.png
walk_2.png
walk_3.png
```

のように安全な一意名を生成する。

---

# 11. ファイル名表示

各セルの下部またはオーバーレイ領域に小さくファイル名を表示する。

単一セル画像なら：

```text
idle.png
```

複数セル画像なら連番を表示する。

例：

```text
walk_01
walk_02
walk_03
...
```

連番は左→右、上→下の順。

元画像が `walk.png` の4×2シートなら、

```text
walk_01
walk_02
walk_03
walk_04
walk_05
walk_06
walk_07
walk_08
```

とする。

表示名はPNG出力には描画しない。

---

# 12. セル選択

セルをクリックするとそのセルをSelected状態にする。

Selectedセルは枠などで明確に表示する。

同時にPreviewもそのセルへ切り替える。

空セルも選択可能とする。

---

# 13. セル位置調整

各セルは、

```text
offsetX
offsetY
```

を持つ。

初期値：

```text
0, 0
```

Selectedセルが存在する状態で、

```text
↑
↓
←
→
```

を押すと、そのセルの画像を1pxずつ移動する。

例：

```text
← : offsetX - 1
→ : offsetX + 1
↑ : offsetY - 1
↓ : offsetY + 1
```

これは元画像を書き換えない。

表示およびPNG出力時にoffsetを適用する。

セル境界からはみ出した部分はクリップする。

位置調整後はDirty状態にする。

---

# 14. Preview

画面右上にPreview領域を常設する。

現在選択されているセルを拡大表示する。

Nearest Neighborで表示し、ドット絵がぼやけないようにする。

Previewにはセル境界を表示する。

---

# 15. Previewナビゲーション

Preview下部に、

```text
[←]   x:[ 3 ] y:[ 2 ]   [→]
```

を配置する。

x/yは現在表示中セルのインデックス。

インデックスはUI上では分かりやすさを優先し、1始まりとする。

内部データは0始まりでよい。

---

## 15.1 ← →

←を押すと左隣のセルへ移動する。

→を押すと右隣のセルへ移動する。

行端では次の行へ移動する。

つまりグリッド全体を、

```text
1 → 2 → 3 → ...
```

の一次元連番として移動できる。

左上より前、右下より後には移動しない。

---

## 15.2 x/y直接入力

x/yへ直接値を入力すると、そのセルへ移動する。

範囲外の値は拒否する。

グリッド側のSelectedセルも同期する。

---

# 16. 前後セルOverlay

Previewに、

```text
☐ 前後セルを重ねる
```

を設置する。

ONの場合：

現在セルを通常表示する。

さらに、

- 1つ前のセル：青
- 1つ後のセル：赤

として半透明で重ねる。

用途はアニメーションフレーム間の位置確認。

概念：

```text
前フレーム = Blue / Alpha 0.4
現在       = Original
次フレーム = Red / Alpha 0.4
```

空セルの場合はそのOverlayを表示しない。

前後セルにもそれぞれのoffsetを適用する。

「前後」はPreviewナビゲーションと同じ一次元セル順序とする。

---

# 17. セルサイズ変更

既に画像が配置されている状態でCell Width / Heightを変更した場合、即座に破壊的変更しない。

以下のダイアログを表示する。

```text
セルサイズを変更します。

既存画像の表示領域を変更するため、
トリミング／余白追加の基準点を選択してください。
```

3×3のAnchor UIを表示する。

```text
┌────┬────┬────┐
│左上│ 上 │右上│
├────┼────┼────┤
│ 左 │中央│ 右 │
├────┼────┼────┤
│左下│ 下 │右下│
└────┴────┴────┘
```

ユーザーがAnchorを選択して確定してからサイズ変更する。

キャンセル可能とする。

---

# 18. サイズ変更アルゴリズム

例：

```text
120×120
↓
100×100
```

中央Anchorなら上下左右10pxずつ削る。

左上Anchorなら、

```text
左 = 0
上 = 0
右 = 20
下 = 20
```

を削る。

逆に、

```text
100×100
↓
120×120
```

の場合は同じAnchor規則で透明領域を追加する。

重要：

**可能な限り元画像自体を加工しない。**

セルのSourceRectおよびoffset等の論理情報によって表現できる場合は非破壊的に保持する。

ただし、元のシート画像を複数セルで共有している場合など、セルサイズ変更によって従来のSourceRect表現が不自然になる可能性がある。

そのためセル内部モデルには最終的な表示領域を表現できる、

```text
sourceRect
offsetX
offsetY
```

等を明示的に持たせる。

「元画像の分割単位」と「現在のセルサイズ」を同一概念として固定しないこと。

---

# 19. 全角文字禁止

入出力対象となるファイル名および必要なパス要素について、ASCII以外の文字を禁止する。

少なくとも以下をチェックする。

- 読み込み画像ファイル名
- JSONファイル名
- PNG出力ファイル名
- assetsへコピーするときのファイル名

日本語・全角英数字等を含む場合は処理を拒否する。

例：

```text
ファイル名に全角文字または非ASCII文字が含まれています。

キャラ歩行.png

半角英数字のファイル名へ変更してください。
```

ただしタイトル入力欄そのものについては、ファイル名として使用するため同様にASCII安全文字のみ許可する。

推奨許可文字：

```regex
[A-Za-z0-9_.-]
```

パス全体に日本語が含まれるWindows環境はあり得るため、親ディレクトリの絶対パスまでは禁止しない。

**ユーザーが指定・生成するファイル名のみ検査対象とする。**

---

# 20. JSON保存
OS標準の保存ショートカットで現在のプロジェクトを保存する。
- Windows: Ctrl+S
- macOS: Cmd+S
初回保存時：
Avaloniaの StorageProvider.SaveFilePicker を使用して保存先を選択する。
WPF / WinFormsの SaveFileDialog や、Avaloniaの旧式・非推奨FileDialog APIは使用しない。
2回目以降：
現在のJSONへ上書き保存する。
保存成功後、
IsDirty = false
とする。

---

# 21. JSON読み込み

Fileメニュー等からJSONプロジェクトを読み込めるようにする。

JSON読み込み時：

1. formatVersion確認
2. 必須フィールド確認
3. assets参照確認
4. 画像サイズ等の整合性確認
5. グリッド復元
6. Preview復元

を行う。

壊れたJSONや不足assetが存在する場合、クラッシュさせずエラー内容を表示する。

---

# 22. PNG出力

完成したグリッドを1枚のPNGへ出力する。

出力サイズ：

```text
width  = CellWidth  * Columns
height = CellHeight * Rows
```

背景は透明。

各セルについて、

- sourceRect
- offsetX
- offsetY

を反映して描画する。

セル外にはみ出す部分はクリップする。

ファイル名初期値：

```text
{Title}.png
```

---

# 23. Dirty管理

以下の操作を行った場合、プロジェクトをDirtyにする。

- タイトル変更
- セル追加
- セル削除
- セル置換
- セル位置調整
- Cell Width変更
- Cell Height変更
- Columns変更
- Rows変更
- その他JSON内容に影響する操作

単なるPreview移動はDirtyにしない。

Overlay ON/OFFもプロジェクトへ保存しないならDirtyにしない。

---

# 24. 未保存終了確認

Dirty状態でアプリを閉じようとした場合、

変更内容が保存されていません。

保存して終了しますか？

[保存して終了]
[保存せず終了]
[キャンセル]

を表示する。

以下を含む、OS上でアプリケーションまたはウィンドウを終了させる通常の操作について、可能な限りすべて同一のDirty確認処理を通す。

Windowsの×ボタン

WindowsのAlt+F4

macOSのウィンドウ終了操作

その他Avaloniaから捕捉可能な通常の終了操作

OS固有の終了処理を個別に実装するのではなく、可能な限りAvaloniaの共通Closing処理へ集約する。

新規プロジェクト作成時、別プロジェクト読み込み時にも、現在のProjectがDirtyなら同様に確認する。
---

# 25. Undo / Redo

初期版から可能なら、OS標準のUndo / Redoショートカットを実装する。

Windows：

Ctrl+Z = Undo
Ctrl+Y = Redo

macOS：

Cmd+Z = Undo
Cmd+Shift+Z = Redo

各OSの一般的なショートカット慣習を優先する。

可能な限りAvaloniaのKeyBinding / HotKey等、クロスプラットフォームな仕組みを使用し、OS固有APIへ直接依存しない。

最低限Undo対象：

画像配置

画像置換

セル削除

offset変更

グリッドサイズ変更

セルサイズ変更

特に矢印キーによる1px移動は、

← ← ← ← ←

を5回別々のUndo履歴にせず、短時間に連続した同方向移動は可能なら1操作へまとめる。

ただしMVP完成を阻害する場合、Undo/Redoは後回しでもよい。

# 26. 推奨データモデル

概念上以下のように分離する。

```text
SpriteProject
 ├─ FormatVersion
 ├─ Title
 ├─ CellWidth
 ├─ CellHeight
 ├─ Columns
 ├─ Rows
 └─ Cells[]

SpriteCell
 ├─ X
 ├─ Y
 ├─ SourceAsset
 ├─ SourceRect
 ├─ OffsetX
 ├─ OffsetY
 └─ DisplayName

SpriteAsset
 ├─ RelativePath
 ├─ Width
 └─ Height
```

同じシートから生成された複数セルは同一SpriteAssetを参照してよい。

---

# 27. 重要な設計原則

## A. 非破壊編集

位置調整・トリミング等で元assetを書き換えない。

可能な限り、

```text
SourceRect
Offset
```

で表現する。

---

## B. ProjectとAssetを分離

セルが直接外部ファイルを参照しない。

```text
外部画像
    ↓ import
assetsへコピー
    ↓
SpriteAsset
    ↓
SpriteCell
```

とする。

---

## C. UI状態とProject状態を分離

SelectedCellやPreview位置など、編集画面だけに必要な情報をJSONデータモデルへ無闇に混ぜない。

---

## D. エラー時にProjectを壊さない

画像読み込み、サイズ変更、JSON読み込みなどは、

1. Validation
2. 変更内容の計算
3. 問題がないことを確認
4. Commit

の順で行う。

Validation失敗時には既存状態を変更しない。

# 31.Codexへの実装上の指示

実装を開始する前にこの計画を読み、データモデルと座標系を先に確定すること。

特に、

Grid座標
SourceRect座標
Offset座標
Preview座標
Export座標

について、それぞれX/Yの正方向と原点を統一すること。

Avaloniaの表示座標系と画像データ側の座標系で、Y方向やRect解釈が食い違わないよう注意する。

画像処理ロジックをUIイベントへ直接埋め込まず、

Import
Split
Resize
Render
Export
Validation

を独立したサービスまたは純粋ロジックとして実装し、可能な部分にはユニットテストを書くこと。

特にResize処理についてはUI実装より先にテストを完成させること。

UI層についてもWindows固有API、WPF、WinFormsへ依存させない。

ファイル選択・保存にはAvaloniaの StorageProvider APIを使用し、現在のAvaloniaで推奨されているクロスプラットフォームAPIを優先する。

キーボードショートカットはOSごとの一般的な操作慣習を尊重する。

少なくとも、

保存:
Windows = Ctrl+S
macOS   = Cmd+S

Undo:
Windows = Ctrl+Z
macOS   = Cmd+Z

Redo:
Windows = Ctrl+Y
macOS   = Cmd+Shift+Z

をサポートする。

これらをOS固有コードの乱立で実現せず、可能な限りAvaloniaのKeyBinding / HotKey等の共通機構を利用する。

WindowsとmacOSで同じJSON Projectを相互に読み書きできること。

Project内ではOS固有の絶対パスを保存せず、asset参照はProject JSONからの相対パスとする。

パス結合等には Path.Combine 等のクロスプラットフォームな.NET APIを使用し、\ や / を前提とした文字列連結をしない。

一度に全Phaseを実装しない。

Phase 1から順番に実装し、各Phase終了時にビルド・テスト・動作確認を行ってから次へ進むこと。

既存Phaseを壊して次のPhaseへ進まないこと。

MVP完成後に初めてUI装飾や追加機能へ進むこと。
